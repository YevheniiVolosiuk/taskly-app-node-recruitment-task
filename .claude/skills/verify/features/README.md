# Taskly verification map

This directory is the maintained source for verifying the user-facing behavior of Taskly's todos. Read the index before driving the app, then use the matching feature file as the recipe.

## Baseline preconditions

- The [skill](../SKILL.md)'s Launch and Doctor steps are done: every doctor line reads `ok`.
- The database starts empty on every `up`. The UI shows the `Add your first task` empty state.
- The browser session is open: `$U open "$WEB"`.

## Driving conventions

- Recipes use `$S`, `$U`, `$WEB`, `$API`, and `$EVIDENCE` from `eval "$(.claude/skills/verify/scripts/stack.sh env)"`.
- Target controls with `getByRole` and the accessible names quoted in each recipe. Class names are generated by styled-components and change between builds.
- Run `$U snapshot --filename=<feature>.<step>.aria.yml` after each step that changes state.

## Proof and skip reporting

- Proof follows the skill's proof standards. Name artifacts `<feature>.<step>`, for example `complete-task.marked.aria.yml`.
- Report an unreachable entry point as unreachable, with the attempted command and the unmet precondition. An entry point counts as verified only through its own path.

## Feature entry contract

Each feature file starts with an H1 title and one paragraph describing the user-visible behavior. It then uses exactly four H2 sections in this order.

1. `Sub-features` lists short IDs with one line for each behavior.
2. `How to get to it (user POV)` lists every user entry point.
3. `Driving it with ui.sh` (or `curl` for the API) starts with `Preconditions:` and uses labeled bullets that pair each user action with an exact command and observable result.
4. `Gotchas` lists traps that can waste or invalidate a verification run.

Keep implementation details out of the map. Name only user paths, stable handles, required state, commands, and observable proof.

## Features

- [Create a task](./create-task.md) covers both create entry points, field validation, and persistence.
- [Complete a task](./complete-task.md) covers marking a task done and back to active.
- [Edit and delete a task](./edit-delete-task.md) covers changing fields and confirmed deletion.
- [Find tasks](./find-tasks.md) covers search, the status filter, and sorting.
- [Todos API](./todos-api.md) covers health and CRUD over HTTP, as the Verification Job runs it.
